About Campus Customs

Campus Customs is a Yale-inspired clothing store: 102 hoodies, crewnecks, quarter-zips, tees and jackets with live size-by-size stock. Customers can browse and filter the catalogue, open product pages with exact inventory, and create an account.

Handsome Dan is the store’s AI shopping assistant (PydanticAI agent, model gpt-5.6-luna through the Portkey gateway). He answers in plain language, uses two database tools (search_products, check_inventory), returns clickable product cards that the backend builds from verified database rows, knows which product page the shopper is on, and saves separate conversations for signed-in customers. There is deliberately no cart or checkout.

Test environment

How the app was started
  • Backend (FastAPI): from hw4/backend with the venv active: uvicorn main:app --port 8000, with CAMPUS_DATA_DIR pointing at a temporary copy of hw4/data. Normal use is the professor’s command uvicorn main:app --reload --port 8000 on the real database.
  • Frontend (React + Vite): npm run dev in hw4/frontend → http://localhost:5173 (proxies /api and /media to port 8000).
  • AI-outage test: a second backend on port 8001 with PORTKEY_BASE_URL set to an unreachable local address (no Portkey traffic).
Test conditions
  • Windows 11; Python venv hw4/.venv; headless Microsoft Edge driven via the DevTools protocol (tests/cdp.py, no extra packages).
  • Viewports: desktop 1280×800, tablet 820×1180, phone 390×844 (plus 360 px for the header fix).
  • All test accounts and conversations were created only in the temporary copy; the real database was not modified (still 3 users).
  • AI calls were kept low: 19 chat messages in total, no repeats for screenshots (except one re-run on phone after a fix).
  • No passwords, keys, cookies or real customer data appear in the screenshots or this report; the professor’s test account is used only through the API, with its email withheld.

Issues found, fixes and limitations

Fixed
Signed-in chat header was cramped

Found: With the longer name “Handsome Dan” (Problem 10) plus the Chats and New chat buttons, the title wrapped onto two lines and “Shopping assistant · chats saved” was squeezed into a narrow column. Found in the signed-in screenshots.

Fix and retest: Panel 380 → 400 px on desktop; title and status kept on one line; slightly tighter header spacing; the redundant “· chats saved” text removed (the line under the input already says chats are saved); header avatar hidden only on phones ≤ 380 px. Re-measured at 1280, 820, 390 and 360 px: no clipping, no overflow.

Fixed
Dan’s head was cut off in the phone sniff/run animation

Found: On phones the 131 px sprite sat in a 104 px box; flexbox shrank it before the 0.8× scale, clipping the right side of each frame. Desktop (132 px box) was unaffected, which is why Problem 10’s desktop checks missed it.

Fix and retest: .dan-activity > * { flex-shrink: 0 }. Retested with a live phone search (turn #17): full Dan visible.

Test tooling
Three problems in the test scripts themselves (not the app)

Found: (1) The UI login check looked for the wrong wording; the app’s message is “That email and password don’t match our records.” (2) The credential-leak check flagged a false positive: a test-account value that the assistant never has access to matched an ordinary word the customer had typed. (3) Requests to localhost took ~2 s each on Windows (IPv6 fallback).

Fix and retest: Corrected the keyword; the leak check now ignores words echoed from the customer’s own question; scripts use 127.0.0.1. All suites were re-run after these changes.

Observations and limitations (not failures)

  • Blunt prompt-injection was stopped by the AI provider’s content filter (turn #7), and the backend replied with its standard polite redirect. To test the model’s own behaviour, two milder probes were added (turns #18–19); it declined both and revealed nothing.
  • Extra round-trip on some general questions: for “Hi Dan! What can you help me with?”, the policy question and the credentials probe, the model first tried an empty product search. The backend’s guard refused it (no search ran, so Dan correctly stayed idle in turns #1, #6 and #19). The cost is one extra model request (~4–5 s instead of ~2 s). Answers are correct; this is a speed observation, not a bug.
  • The no-match search (“umbrellas or coffee mugs”) made the tool’s loose fallback return 98 weak matches; the model correctly said nothing matched and showed no cards.
  • Dan is shown for at least 0.7 s per status (Problem 9’s readability pacing), so the sniff-walk can continue briefly after a fast (≈40 ms) database search has finished. It never starts before the real event. If the reply arrives first, remaining statuses are skipped (turn #17, a cached reply in 1.3 s, went straight from sniff to the answer).
  • No product is sold out in every size in this database, so the “fully sold out” badge could not be exercised with real data. Size-level sold-out handling was tested (612 inventory labels; Boola Boola T-Shirt size L in chat).
  • Screenshots were taken with headless Microsoft Edge driven through the DevTools protocol at exact sizes (1280×800 desktop, 820×1180 tablet, 390×844 phone). Reduced motion was tested with the browser’s real prefers-reduced-motion: reduce emulation.
  • Earlier-turn screenshots in the signed-in conversation (#10–#13) were taken before the header fix, so they still show the cramped header.
